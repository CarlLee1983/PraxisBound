# PROTOTYPE — TST-022 Review Projection 資訊架構

拋棄式原型，只存在於 `prototype/tst-022-review-projection` 分支，不合併進 main。

## 要回答的問題

TST-022 第一版 HTML 依來源檔案逐份排列、每份文件印兩次，非執行者讀起來像流水帳（#85）。
以需求為主軸重組後，哪一種呈現最能讓讀者判斷「確認定義或提出修訂」？

## 做法

`build.mjs` 讀取真實 BR-TST-022 批次（ADR-014、`specs/features/batch-review/spec.md`、
TST-021、TST-022），產出一頁含三種變體的靜態 HTML，以 `?variant=` 與底部切換列切換：

* A 編輯式長文：左側需求目錄，逐條需求依序展開。
* B 總覽矩陣＋逐條展開：首屏需求矩陣，下方每條需求一張卡片。
* C Spec／Story 並排對照：每條需求左右兩欄逐列對照。

```sh
node build.mjs <repo-root> <output.html>
```

首屏「審閱導言」是示範文字（manifest 尚無 `preface` 欄位）；診斷區只放數量。

## 結論（2026-09-18）

採用 B，並定案：

* 首屏順序：標題 → 審閱導言 → 需求總覽矩陣 → 批次目標 → 不包含 → 決策約束 → 診斷。
* 需求卡片預設收合；從矩陣連結進入時展開並捲到該卡；列印時全部展開。
* 卡片內順序：需求驗收 → 執行驗收 → Story 重點 → 需求細節。
* 矩陣只呈現事實（條數、「未寫明」），不以顏色或警示判斷差異。

觀察：Story 為英文、Spec 為中文，並排時落差明顯；這是撰寫端問題，Renderer 不翻譯。
矩陣直接暴露 R-002 未寫「不包含」，以及需求驗收與執行驗收條數差異（R-003：7 對 10）。
